# qk-kernels — kernel contract and Rust/NumPy parity specification (v0.1)

## Why

`quantibbler`'s performance-critical CPU paths must live in the Rust extension
`quantibbler-kernels`, with a NumPy reference as the executable specification
(`openspec/config.yaml`, Architecture). Today the crate is an empty scaffold
(`backend_version()` only) and `src/quantibbler/kernels.py` exposes only
`backend()`. Before either lane (qk-representation, qk-ptq) can build solvers
on top of accelerated primitives, the kernel surface itself needs a pinned
contract: exact function semantics, the packed bit layout, dtype rules,
dispatch behavior, and the parity gate that keeps Rust and NumPy interchangeable.

The v0.1 surface is the shared primitive layer that both method paths consume:

- Binary packing (`pack_bits` / `unpack_bits`) — the packing stage of
  [NQ] Sec 3.1 (Fig. 2: −1 → 0, +1 → 1, 8-bit blocks); every serialized byte
  of BPW flows through this layout.
- Sign estimation (`sign_estimate`) — the `sign(·)` quantizer applied to latent
  factors in [NQ] Sec 3.2 Step 3 (Eq. 10 finalization) and the B-update of
  [LB2] Sec 4.4 Algorithm 1.
- Packed binary matvec/matmul — the packed-domain products used during
  reconstruction with frozen packed binaries ([NQ] Sec 3.3: "bit-packed binary
  weights throughout").
- Joint-ITQ (`joint_itq`) — the LB-path initializer [LB2] Sec 4.4 (alternating
  Procrustes over the joint latent manifold Z = [Û; V̂]).

The heavy LB-ADMM inner algebra ([NQ] Sec 3.2 Step 2-2, Eq. 5–6) stays in NumPy
for v0.1; only these five primitives are contracted here.

## What Changes

- Specify the v0.1 kernel surface: `pack_bits`, `unpack_bits`, `sign_estimate`,
  `packed_matvec`, `packed_matmul`, `joint_itq`, all NumPy-first with a Rust
  twin per function.
- Pin the packed layout contract: uint8 bitplanes, row-major, little-endian
  bit order within each byte, +1 → bit 1, −1 → bit 0, zero-padded row tails
  (the layout agreed across the qk-* lanes).
- Specify dispatch semantics: `backend()` returns `rust` |
  `numpy-reference`; graceful automatic fallback when the extension is absent;
  explicit `QUANTIBBLER_BACKEND` override that fails loudly; per-call
  `backend=` override for parity probes.
- Specify the parity test strategy: scenario-ID-named probe tests on both
  sides (pytest comparing backends in-process; cargo tests against committed
  JSON fixtures generated by the NumPy reference), float64 rel 1e-12 for float
  outputs and byte-identical comparison for packed outputs.
- Add the dual-face architecture mandated by the new Component decomposition
  in `openspec/config.yaml`: the crate exposes ONE kernel implementation with
  TWO consumption faces — a plain rlib API (linked directly by the pure-Rust
  server, `quantibbler-server`) and a PyO3 extension module (consumed by the
  Python compressor for quantized-side inference in parity probes and
  pipeline gates, instead of reimplementing kernels in torch or NumPy). Core
  kernel logic moves to a pyo3-free layer; the PyO3 face becomes a thin
  binding; face parity (same fixture through both faces: packed bits
  identical, float64 rel 1e-12) extends the existing Rust-vs-NumPy parity;
  `crate-type = ["cdylib", "rlib"]` coexistence and the opt-in
  `extension-module` feature are pinned so both faces build and test green in
  one workspace and `cargo test` links without libpython.
- Mark this change **invariant-touching** (see Impact).

## Impact

- **Invariant-touching — kernels contract and storage format.** The packed
  uint8 layout defined here becomes the byte-level convention that serialized
  artifacts and effective-BPW accounting (counted from serialized bytes,
  `openspec/config.yaml` Method invariants) are measured against. Changing the
  layout after artifacts exist would invalidate every stored bitplane and
  break Rust/NumPy interchange; compatibility impact: any future layout change
  requires a new capability delta and a format version bump, not an edit here.
- Affected spec capabilities: `qk-kernels` (new). No existing spec capabilities
  exist yet; sibling capabilities (representation, PTQ solvers) will consume
  this one by name and must not redefine the layout.
- The NumPy implementations remain the executable specification; the Rust path
  must match within the pinned tolerances on every probe test
  (`openspec/config.yaml`, Verification gates).
- **Dual-face consumers of `quantibbler-kernels`** (Component decomposition,
  `openspec/config.yaml`): the pure-Rust server (`quantibbler-server`, serving
  change by the qk-server lane) links the rlib face directly; the Python
  compressor consumes the PyO3 face for quantized-side inference (parity
  probes, pipeline gates). Both faces are specified and parity-gated here;
  the server's endpoint surface is owned by the serving change and only cited
  by name. A kernel-behavior change therefore lands in this change first, and
  both consumers inherit it through the same crate — no behavior fork is
  possible without violating config.
- The NumPy-vs-Rust parity contract extends to face parity: the same fixture
  through the rlib face and the PyO3 face yields packed outputs
  byte-identical and float64 outputs within rel 1e-12.

## Non-goals

- **No GPU kernels.** Rust kernels are CPU-only in v0.1; GPU/array compute
  stays in PyTorch (`openspec/config.yaml`, Architecture).
- **No training/autograd kernels in v0.1.** The [LB] Sec 3 QAT path (STE
  gradients, multi-scale compensation, distillation) is out of scope;
  `sign_estimate` is contracted only as the deterministic forward quantizer.
- **No LB-ADMM solver kernels.** The ADMM inner loop ([NQ] Sec 3.2 Step 2-2:
  Cholesky solves, SVID) remains NumPy in v0.1; candidate for a future kernel
  delta once profiles justify it.
- **No packed×packed binary matmul.** v0.1 contracts packed×dense-float only
  (open question for qk-representation).
- **No float32 fast path.** float64 is the default numerics per config; a
  documented opt-in float32 accelerator may come later, never silently.
- **No BLAS/LAPACK linkage in Rust.** The C/C++/Cython/CUDA-C++ dependency ban
  extends through the build graph; Rust linear algebra must be pure Rust.
- **No serialization format.** This change pins the in-memory packed layout
  only; on-disk artifact framing belongs to qk-representation.
- **No threading/parallelism contract.** v0.1 kernels are single-threaded
  deterministic; parallel schedules are a future, parity-gated change.
