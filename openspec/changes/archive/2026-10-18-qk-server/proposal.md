# Change: qk-server — pure-Rust OpenAI-compatible inference server for qpk1 models

## Why

The binding component decomposition in `openspec/config.yaml` splits quantibbler
into a Python compressor/trainer and a pure-Rust SERVING component "in the
llama.cpp / vLLM shape": an OpenAI-compatible HTTP API (`/v1/chat/completions`,
`/v1/completions`, `/v1/models`, `/health`) that loads qpk1 model directories
from local paths or network-volume mounts and serves token streaming, on tokio +
axum with the tokenizers crate for BPE. No such component exists — the qpk1
artifacts defined by the `qk-representation` lane have no Rust consumer, so the
end-to-end story (compress -> serialize -> serve) cannot be exercised, and the
compressed-deployment claim the papers build toward ([NQ] App. F storage
discipline feeding real inference; [LB] App. D) has no implementation home. The
`qk-kernels` lane is exposing the rlib face of `quantibbler-kernels` precisely so
one parity-gated kernel implementation serves both faces; this change specifies
the server that consumes it: binary `quantibbler-server`, CPU-first in v0.1,
with no Python dependency, no embedded interpreter, ever (config).

## What Changes

- New capability `qk-server` (this change), specified as ADDED requirements:
  - a single-process server binary `quantibbler-server` taking a model
    directory path and port via clap, which reports ready only after the qpk1
    model directory loads successfully (fail-closed, no partial model);
  - OpenAI-compatible endpoints: `GET /v1/models`, `POST /v1/chat/completions`
    (streaming and non-streaming), `POST /v1/completions` (streaming and
    non-streaming), `GET /health`;
  - streaming via server-sent events in the OpenAI chunk format, terminating
    with the `data: [DONE]` sentinel;
  - errors returned in the OpenAI error JSON envelope with a documented
    status-code map (400 / 404 / 500 / 503);
  - concurrency against the single loaded model: weights shared as immutable
    state, requests executed independently;
  - v0.1 serving is CPU-only through the rlib face of `quantibbler-kernels`
    (capability `qk-kernels`); the GPU substrate is a recorded design decision
    gated on profiling evidence (config GPU policy), not a dependency.
- Consumes sibling capabilities BY NAME, without modifying them:
  `qk-representation` (qpk1 container, canonical bit packing, BPW accounting)
  and `qk-kernels` (packed binary kernels, Rust/NumPy parity gates). This
  change REQUIRES the `qk-representation` lane to gain an explicit
  model-directory manifest requirement — tokenizer files carried in the model
  directory, layer naming/ordering, non-quantized component storage (see Impact
  and design OQ1).
- No implementation in this change: proposal, design, tasks, and the delta
  spec only.

## Impact

- **Affected specs:** creates `specs/qk-server/spec.md` on archive. No existing
  spec is modified (the main `openspec/specs/` tree is empty today).
- **Affected code (future implementation landing against this spec):** new
  `crates/quantibbler-server/` pure-Rust crate (edition 2024, MSRV 1.85,
  Apache-2.0) as a member of a root Cargo workspace alongside
  `quantibbler-kernels`; a root `Cargo.toml` workspace manifest. No Python
  changes: the compressor package and its pytest suite are untouched and must
  stay green; the server is never a uv workspace member and gains no pyproject.
  The kernels crate's public API is untouched by this change — its rlib face is
  the `qk-kernels` lane's scope; this change consumes it by capability name
  only.
- **Cross-lane dependency:** model-directory acquisition (tokenizer files +
  layer manifest) is an explicit Open Question owned by the `qk-representation`
  lane; this change flags that capability as needing the manifest requirement.
  Server work unblocks meanwhile via fixture model dirs generated byte-level
  against qpk1's pinned layout (design D3).
- **Not invariant-touching:** this change alters no kernel contract and no
  storage-format byte; it consumes both as pinned by `qk-representation` and
  `qk-kernels`. If the manifest extension lands in `qk-representation`, that
  lane owns its version/compatibility statement.

## Non-goals

- **No training or compression in the server.** The server never runs PTQ/QAT,
  never computes quantization, and never writes qpk1 artifacts; those belong to
  the compressor ([NQ] Sec 3; [LB] Sec 3; config Component decomposition).
- **No Python.** No embedded interpreter, no PyO3 face, no Python dependency
  anywhere in the server build graph; the compressor is never a server
  dependency (config: "No Python dependency, no embedded interpreter, ever").
- **No model zoo / runtime downloads.** No network access at runtime; models
  arrive as local paths or network-volume mounts; downloading models is the
  caller's job, documented but not built (config Method invariants).
- **No multi-model registry in v0.1.** One process serves exactly the one
  model directory given at startup; no registry of many models, no hot-swap.
- **No GPU substrate in v0.1.** CPU packed kernels only (config GPU policy);
  the substrate evaluation (candle / mistral.rs / cubecl) is recorded in
  design as a decision record, not adopted as a dependency.
- **No TLS or authentication in v0.1.** Plaintext HTTP on a caller-chosen
  interface (localhost default); TLS termination is the deployment's job. This
  also keeps C/C++-building TLS stacks (ring/aws-lc) out of the build graph,
  per the config build-graph ban.
- **No continuous batching or paged KV cache.** v0.1 uses a simple,
  permit-bounded decode path with a plain per-sequence KV cache; scheduler
  sophistication is future work once profiles justify it.
